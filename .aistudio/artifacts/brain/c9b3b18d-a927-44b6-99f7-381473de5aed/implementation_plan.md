# UMAR MENS SHOP — Комплексный Архитектурный План Платформы (Ревизия 2)

Промышленная архитектура коммерческой системы для UMAR MENS SHOP с нулевым допущением компромиссов: строго изолированные зоны доступа (Store, Customer, Staff, Admin) с независимыми Layout-компонентами, серверный контроль прав на уровне каждого API и объекта, безопасный адаптер `PaymentProvider`, архитектура базы данных с поддержкой PostgreSQL и локального dev-драйвера, повариантный складской учет с ACID-транзакциями, защита от гонок и автоматизированные тесты безопасности.

## 1. Overview & Core Concept

- **Что это**: Корпоративная система электронной коммерции, объединяющая публичную fashion-витрину UMAR MENS SHOP, личный кабинет покупателя, операционный интерфейс обработки заказов (Staff) и управленческую панель владельца (Admin).
- **Ключевой принцип безопасности**: *Полная изоляция интерфейсов и данных*. Обычный клиент ни в DOM, ни в исходном JavaScript-бандле, ни в API-ответах не получает доступа к остаткам складов, себестоимости, списку сотрудников, финансовой статистике или ключам интеграций.
- **Брендинг**: Премиальный мужской магазин в Алматы. Фирменный знак — оригинальный векторный/высококачественный логотип **UMAR | MEN'S SHOP** из приложенного файла (`/public/assets/aistudio/_____cecc8cff.jpg`), строгая чёрно-белая монохромная эстетика, качественная типографика без кричащих AI-элементов.

## 3. Key Product Decisions & Trade-Offs

### Решение 1: Безопасный платёжный адаптер PaymentProvider (Пункт 2)
- **Архитектура**:
  ```typescript
  interface PaymentProvider {
    readonly providerId: string;
    createPaymentSession(params: CreatePaymentParams): Promise<PaymentSessionResult>;
    verifyWebhookSignature(rawBody: string, headers: Record<string, string>): boolean;
    processWebhookEvent(payload: unknown): Promise<PaymentEventResult>;
    checkPaymentStatus(paymentId: string): Promise<PaymentStatusResult>;
    refundPayment(paymentId: string, amount: number, reason: string): Promise<RefundResult>;
  }
  ```
- **Реализация сейчас**:
  - `SandboxPaymentProvider`: Тестовый провайдер с явным статусом `DEMO / SANDBOX`. Активируется только в режиме разработки. Имеет симулятор проверки оплаты с фиксацией в журнале `payment_events`.
  - `KaspiPaymentAdapter`: Заготовка промышленного адаптера, ожидающая боевые параметры (`KASPI_PAY_MERCHANT_ID`, `KASPI_PAY_CERT_PATH`, `KASPI_API_SECRET`). Если ключи отсутствуют, адаптер переходит в состояние `NOT_CONFIGURED` и информирует владельца в `/admin/integrations`.
  - Никакой заказ не переводится в статус `paid` по простому клиентскому редиректу. Перевод статуса выполняется исключительно серверным обработчиком.

### Решение 2: База данных для Production и Development (Пункт 3)
- **Продакшн-стратегия**: Полная схема базы данных спроектирована под стандарт ANSI SQL / PostgreSQL (для развёртывания в Supabase, Neon или Cloud SQL). Предоставляются SQL-миграции (`migrations/001_init.sql`).
- **Среда разработки в AI Studio**: Используется локальный реляционный SQL-движок с хранением файла БД на сервере Express. Реализован уровень абстракции репозиториев (Repository Pattern), что позволяет переключить источник данных на управляемый PostgreSQL заменой переменной окружения `DATABASE_URL` без изменения бизнес-логики.
- **Транзакции**: Все критические операции (списание остатков, создание заказа, приход на склад) выполняются строго в рамках изолированных транзакций (`BEGIN TRANSACTION ... COMMIT`).

### Решение 3: Складской учёт и предотвращение гонок остатков (Пункт 6)
- **Учёт вариантов**: У каждого товара фиксируются варианты в таблице `product_variants` (`variant_id`, `product_id`, `sku`, `size`, `color`).
- **Таблица остатков `inventory`**: Поля `variant_id`, `warehouse_id`, `quantity` (физический остаток), `reserved_quantity` (в резерве), `min_threshold` (порог для алерта).
- **Формула доступного остатка**:
  $$\text{available} = \text{quantity} - \text{reserved\_quantity}$$
- **Защита от оверселлинга**:
  ```sql
  UPDATE inventory 
  SET reserved_quantity = reserved_quantity + :qty 
  WHERE variant_id = :variant_id 
    AND (quantity - reserved_quantity) >= :qty;
  ```
  Если затронуто 0 строк, транзакция откатывается и клиент получает ошибку: «Товар выбранного размера был выкуплен другим покупателем».
- **Срок резерва**: 15 минут. Фоновый таймер проверяет просроченные заказы в статусе `awaiting_payment` и освобождает `reserved_quantity`.

### Решение 4: Интеграция Telegram Bot API (Пункт 7)
- **Реализация**: Серверный модуль `TelegramService`. Если `TELEGRAM_BOT_TOKEN` не задан в `.env`, сервис переходит в пассивный режим: возвращает статус `DISCONNECTED`, выводит в админке подробную инструкцию по созданию бота через `@BotFather` и генерации Webhook URL.
- **Изоляция**: Падение или задержка сети Telegram Bot API перехватывается блоком `try/catch` с записью в системный журнал и ни при каких обстоятельствах не блокирует оформление заказа на сайте.
- **Идемпотентность**: Таблица `telegram_updates` хранит обработанные `update_id` для предотвращения дублирования заказов при повторных попытках отправки вебхуков Telegram.

### Решение 5: Безопасный Bootstrap и матрица прав доступа (Пункты 5 и 8)
- **Инициализация владельца**: Первый аккаунт `OWNER` создаётся либо через CLI-скрипт инициализации `npm run bootstrap:owner`, либо считывается из серверных переменных окружения `INITIAL_OWNER_EMAIL` и `INITIAL_OWNER_PASSWORD`.
- **Запрет эскалации прав**: Публичная регистрация (`POST /api/auth/register`) намертво зафиксирована на назначение роли `CUSTOMER`. Сервер полностью игнорирует любые попытки передать поле `role` в теле запроса.
- **Объектные проверки (Object-Level Authorization)**:
  - `GET /api/orders/:id`: Заказ отдаётся, только если `order.customer_id === req.user.id` ЛИБО у сотрудника есть разрешение `orders:read_all`.
  - Изменение цен: Разрешено только пользователям с явным правом `pricing:update` (только `OWNER`).
  - Управление сотрудниками: Разрешено только `OWNER`.

## 4. Technical Architecture & Test Strategy

### Схема сущностей БД (27 таблиц)

1. **Безопасность и пользователи**: `users`, `roles`, `permissions`, `role_permissions`, `user_roles`, `user_sessions`, `audit_logs`.
2. **Клиенты**: `customers`, `customer_addresses`, `customer_favorites`.
3. **Каталог (с пометкой DEMO)**: `categories`, `products`, `product_variants`, `product_images`.
4. **Склад и WMS**: `warehouses`, `inventory`, `inventory_movements`, `inventory_adjustments`.
5. **Заказы и корзина**: `carts`, `cart_items`, `orders`, `order_items`, `order_status_history`.
6. **Платежи и шлюз**: `payments`, `payment_events`.
7. **Коммуникации и интеграции**: `conversations`, `messages`, `telegram_updates`, `store_settings`.

### Автоматизированный проверочный комплекс (Пункт 10)

В проект включается независимый серверный тест-сьют `server/tests/security-audit.test.ts`, проверяющий:

1. **Test 1 (RBAC Route Guard)**: Неавторизованный пользователь делает запрос к `GET /api/admin/analytics` $\to$ Получает `401 Unauthorized`.
2. **Test 2 (Privilege Escalation)**: Пользователь `CUSTOMER` делает запрос к `GET /api/admin/inventory` $\to$ Получает `403 Forbidden`.
3. **Test 3 (Object-Level Access)**: Покупатель A пытается запросить заказ покупателя B (`GET /api/orders/{id_B}`) $\to$ Получает `404 Not Found / 403 Forbidden`.
4. **Test 4 (Role Isolation)**: Менеджер (`MANAGER`) пытается изменить настройки платёжного шлюза `POST /api/admin/settings` $\to$ Получает `403 Forbidden`.
5. **Test 5 (Price Tampering)**: Кладовщик (`WAREHOUSE`) пытается изменить цену товара `PATCH /api/products/{id}` $\to$ Получает `403 Forbidden`.
6. **Test 6 (Concurrency & Race Condition)**: Два параллельных запроса резервируют последнюю единицу товара (остаток = 1) $\to$ Ровно один запрос успешен (200), второй получает отказ о нехватке остатка (409 Conflict).
7. **Test 7 (Webhook Idempotency)**: Повторная отправка одного и того же события оплаты `payment_id` $\to$ Второй запрос не списывает остаток повторно и возвращает статус `ALREADY_PROCESSED`.
8. **Test 8 (Public Data Leakage)**: Публичный эндпоинт `/api/catalog` не возвращает поля `cost_price`, `supplier_info`, `internal_notes` или физические остатки по складам.

## 5. Порядок Реализации (Step-by-Step)

1. **Шаг 1: Инфраструктура, Модель Данных и Безопасный Bootstrap**:
   - Настройка сервера Express (`server.ts`) с поддержкой API-маршрутов и раздачи Vite.
   - Инициализация схемы реляционной БД (27 таблиц) с индексами и внешними ключами.
   - Создание безопасного bootstrap-скрипта для первого владельца.
   - Загрузка демонстрационного каталога мужской одежды с явными плашками `[DEMO]`.
2. **Шаг 2: Серверная Аутентификация и Защитные Middleware**:
   - Сессионные токены с проверкой срока жизни.
   - Гранулярные middleware: `authenticate`, `requirePermission(perm)`, `requireObjectOwnership`.
   - Защита от подмены ролей в `POST /api/auth/register`.
3. **Шаг 3: Архитектура Layout-компонентов и Storefront**:
   - Интеграция оригинального логотипа UMAR MENS SHOP.
   - Разделение фронтенда на `StoreLayout`, `CustomerLayout`, `StaffLayout`, `AdminLayout`.
   - Публичные страницы: Главная с акцентом на мужской стиль, Каталог с фильтрами по размерам, Карточка товара с выбором вариантов, Корзина, Checkout.
4. **Шаг 4: Личный кабинет покупателя (`/account`)**:
   - Профиль, просмотр личной истории заказов, адреса доставки.
   - Безопасный трекинг гостевых заказов через токен.
5. **Шаг 5: Склад и Внутренние Рабочие Системы (`/staff` и `/admin`)**:
   - Складской модуль: повариантные остатки (SKU + размер + цвет), приход товара, комплектация заказов.
   - Панель менеджера: обработка заказов, CRM-диалоги (публичные ответы vs служебные заметки).
   - Панель владельца: финансовая аналитика, управление ролями, аудит действий.
6. **Шаг 6: Платёжный Адаптер и Telegram-Модуль**:
   - `PaymentProvider` с тестовым изолированным sandbox-режимом.
   - `TelegramService` с обработкой webhook и индикатором статуса подключения («Не подключено» при отсутствии токена).
7. **Шаг 7: Автоматизированные тесты и Верификация**:
   - Запуск проверочного набора тестов безопасности (8 сценариев матрицы прав и атак).
   - Компиляция и сборка проекта (`npm run build`).
